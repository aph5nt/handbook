MVCC: readers never block writers

A long report starts at transaction 110 and reads row 7. Meanwhile the app updates row 7 twice. MVCC (Multi-Version Concurrency Control) keeps every version, so the report and the app each read the version their snapshot can see. Nobody waits. The second tab shows the bill: old versions nobody may clean up.

Where you meet it

      
PostgreSQL and Oracle use MVCC so reads stay fast under writes. PostgreSQL's cleanup is VACUUM. Column stores do a cousin of it: a delete writes a mask, and compaction rewrites the segment later.

    

    

      
The practical choice

      
Keep transactions short. Run long analytics on a warehouse copy, not on the app database. Remember that snapshots are not serializability: write skew still passes unless the engine adds SSI (Serializable Snapshot Isolation).
