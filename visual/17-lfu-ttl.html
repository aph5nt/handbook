LFU and TTL

A decoded-ABI cache holds 3 contracts. A and B are hot. Then a batch job reads three one-off contracts X, Y and Z. LRU (least recently used) and LFU (least frequently used) face the same requests. TTL (time to live) is the third rule, about freshness.

Where you meet these rules

      
Redis maxmemory-policy: allkeys-lru or allkeys-lfu, plus a TTL per key. Caffeine, the Java cache, uses W-TinyLFU: a small LRU window in front of a frequency filter, so it resists scans and still adapts.

    

    

      
The choice you make

      
Bound the size with LRU or LFU. Bound staleness with TTL. A token price cached for 60 seconds needs a TTL because the value goes stale, not because memory is short. Add jitter so keys set together do not expire together.
