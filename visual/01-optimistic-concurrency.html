Optimistic concurrency: the aggregate version

Two requests charge the same wallet at the same moment. Each loads it, checks the rule and saves. Without a version number, one of them silently wins. Press Next.

Where you meet it

      
Postgres or MySQL: a version column and UPDATE ... WHERE id = ? AND version = ?. Kubernetes: every object carries a resourceVersion, and a stale update gets 409 Conflict. HTTP: an ETag with If-Match. Event stores: append with an expected stream version.

    

    

      
The practical choice

      
Give every aggregate a version and check it on every save. On a conflict, reload and run the command again, a few times at most. Choose a pessimistic lock (SELECT ... FOR UPDATE) only when conflicts are frequent and retries would be wasteful.
