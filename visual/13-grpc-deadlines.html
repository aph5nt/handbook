gRPC streams, HTTP/2 and deadlines

A sync service streams blocks from an indexer, and the indexer fetches them from a chain node. Then the node becomes slow. Press Next and compare calls with no deadline to calls whose deadline is passed down.

The code that runs this step

The lit lines are the ones the current step runs. The hops are net/http handlers and the deadline travels in a grpc-timeout style header, because the program uses the standard library only. Real gRPC does the same with its own header. One story second is one millisecond. Full program: handbook/code/13-grpc-deadlines/main.go (go run .).

Where you meet it: an indexer streaming blocks

      
Server streaming with a deadline per batch, retries with jitter, and a second node to fail over to.

    

    

      
Where you meet it: load balancing

      
HTTP/2 keeps one long connection, so a plain connection-level load balancer sends every call to one pod. Use a balancer that spreads requests, such as a service mesh or client-side balancing.
