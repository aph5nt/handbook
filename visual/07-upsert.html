Upsert: a write you can replay

An indexer writes block 9,506's transfers, then crashes before it saves its checkpoint. On restart it writes block 9,506 again. Watch a plain INSERT fail or double the rows, then watch an upsert keyed on (tx_hash, log_index) leave the table exactly as it was.

Where you meet it

      
An indexer replaying a page after a crash. A sync from a supplier feed that upserts each product by its supplier id. StarRocks primary key tables: a load with a key that already exists replaces the old row.

    

    

      
The practical choice

      
Put a unique key on the natural identity first: without it there is no conflict to detect. In replayable writes set values from the source, never add to them. In SQL Server, MERGE needs a HOLDLOCK hint to be safe with concurrent writers.
