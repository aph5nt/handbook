Idempotent consumer: twice has the same effect as once

A top-up event renews a subscription by one month. Kafka and the outbox may deliver that event twice. Watch how the consumer makes the second delivery harmless. Press Next.

Where you meet it

      
A Kafka consumer group after a rebalance. A webhook handler that the sender retries on timeout: Stripe sends an event id for exactly this. A StarRocks primary-key table, where loading the same block twice upserts the same rows. An HTTP API with an Idempotency-Key header for payments.

    

    

      
The practical choice

      
Give every event a unique id at birth. Store processed ids in the same transaction as the effect, with a unique key. Prefer effects that are idempotent by nature: set a value, upsert by a business key. Never rely on the broker for exactly-once effects.
