CPU cache lines and false sharing

Eight indexer workers each count blocks in their own slot of one array, and adding workers makes it slower. Press Next and watch one 64-byte cache line bounce between two cores. Then switch tabs and pad the counters apart.

Where you meet it

      
Per-worker counters and metrics in a Go or Java hot loop. Java has @Contended to pad fields. Go's runtime pads its own per-processor structures. Reading an array in order is fast for the same reason: the CPU loads the next line ahead.

    

    

      
The practical choice

      
Only for hot loops, after a profile shows it. Pad hot variables written by different threads to 64 bytes, or keep counts local and merge at the end. Request handlers never need this.
