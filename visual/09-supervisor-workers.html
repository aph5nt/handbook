Supervisor and workers

A change has three independent tasks: add a database migration, update a dashboard, fix a parser. One supervisor agent splits the work. Three worker agents build in parallel, each in its own git worktree. Watch the briefs go out and the reports come back. Then see what happens when a worker says DONE and has no proof.

Where you meet it

      
A Claude Code harness: the main session plans, spawns one executor per task in its own worktree, then a reviewer that sees the code and not the implementer's reasoning. The main session alone owns commits, memory and the answer to the human. LangGraph and similar frameworks call it the supervisor pattern.

    

    

      
The practical choice

      
The worker knows only its brief, and the supervisor sees only the report. So write the brief like one for a peer: the goal, the files to read, what is already ruled out. Ask for a fixed report shape: DONE, DONE_WITH_CONCERNS, NEEDS_CONTEXT or BLOCKED. Accept DONE only with the command that proves it and its output.
