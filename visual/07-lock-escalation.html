Intent locks and lock escalation

A nightly job wants to lock the whole swaps table while writers hold row locks. Watch the intent flag on the table save it from checking millions of row locks. Then open the second tab: a bulk update holds so many row locks that the engine swaps them for one table lock, and every other writer stalls.

Where you meet it

      
SQL Server escalates row locks to a table lock at about 5,000 locks held by one statement. MySQL InnoDB uses intention locks to guard table locks and DDL (Data Definition Language, such as ALTER TABLE). PostgreSQL never escalates, because row locks live in the rows themselves.

    

    

      
The practical choice

      
Split a bulk update or delete into batches below the escalation size, each its own short transaction. Where the engine allows, turn escalation off for one hot table. In PostgreSQL, watch ALTER TABLE instead: it waits for every open reader of the table.
