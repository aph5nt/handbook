Write-behind: fast writes, a window of loss

Every page view bumps a counter. Writing each one to the warehouse would mean thousands of tiny inserts a second. Press Next and watch Redis take the writes and a flusher batch them, then watch a crash lose the unflushed window.

Where you meet it

      
View counts, rate limits and metrics that are written far more than read. An actor that holds device state and snapshots it later. CPU caches and disk controllers, which write back to memory and disk for the same reason.

    

    

      
The practical choice

      
Use it only where losing a short window is acceptable, and name the window. Put a durable log in front if it is not acceptable. Make the flush idempotent with a batch id.
