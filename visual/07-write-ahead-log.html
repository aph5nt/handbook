Write-ahead log: why a commit survives a crash

A payment sets wallet 7 from 10 to 2 and commits. One millisecond later the server loses power. The changed table page was still only in memory. Watch the write-ahead log (WAL) bring the payment back. The second tab turns the flush off.

Where you meet it

      
PostgreSQL: the WAL is both crash recovery and replication, because replicas replay the same log stream. Kafka: the log is the product, built on the same idea. Hardware: the disk's flush latency sets the commit latency.

    

    

      
The practical choice

      
Keep fsync on, always: with it off a crash can corrupt the database. PostgreSQL's synchronous_commit = off is the safe way to trade: a crash loses the last moments of commits, but nothing is corrupted. Use it only for data you can afford to lose.
