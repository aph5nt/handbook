UUID or sequential keys: where a new key lands

An order service in PostgreSQL inserts orders. Each new key must go into the B-tree index, a row of sorted pages. Watch where a sequential key lands, then where a random UUIDv4 (Universally Unique Identifier, version 4) lands once the index no longer fits in memory.

Where you meet it

      
App tables in PostgreSQL keep a BIGINT identity as the key inside and show a UUID in URLs. Event ids made before the insert, for idempotency or on a phone that is offline, use UUIDv7. Chain data already has a unique natural key, tx_hash.

    

    

      
The practical choice

      
If the database can hand out ids, use a BIGINT. If ids must be made outside the database, use UUIDv7: it starts with a millisecond timestamp, so new keys land at the end of the index like a counter. Avoid UUIDv4 as the primary key of a big B-tree table.
